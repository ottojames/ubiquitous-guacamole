## Iteration 13 - Task 2.1: Debug Current Flow (Admin Login Infinite Spinner)
- **What was implemented**: Added comprehensive console logging to trace auth state and identify redirect loop cause
- **Files changed**:
  - `src/components/admin/AdminProtectedRoute.tsx` - Added detailed logging on every render and useEffect
  - `src/contexts/UnifiedAuthContext.tsx` - Added logging to `canAccessAdmin()` showing all conditions checked

- **Key logging added**:
  - AdminProtectedRoute: logs `loading`, `hasUser`, `userEmail`, `hasSession`, `isPlatformAdmin`, `adminRole`, `role`, `appMetadata` on every render
  - canAccessAdmin(): logs all inputs and which condition granted/denied access
  - Admin Login: logs render state and redirect decisions (already admin → dashboard, user but not admin → stay, no user → show form)
- **Redirect loop cause identified**:
  - After `signInAsAdmin()` returns success, Login page immediately navigates to `/admin/dashboard`
  - But UnifiedAuthContext `loading` may still be `true` (waiting for `onAuthStateChange` callback)
  - AdminProtectedRoute may see partial state (no user yet, or user but context not fully updated)
  - This could cause redirect back to login, creating a loop
- **Solution direction for Task 2.3**:
  - Add `isInitialized` flag to UnifiedAuthContext that only becomes true after initial auth state is fully loaded
  - AdminProtectedRoute should wait for both `!loading` AND `isInitialized` before making redirect decisions
- **Learnings for future iterations**:
  - The race condition is between navigation (immediate) and context state update (async via onAuthStateChange)
  - 49 failing tests remain pre-existing - same count as before (Phase 6 work)
  - TypeScript errors in cypress/, e2e/, scripts/ are pre-existing and not blocking
  - Next is Task 2.2: Fix Admin User Metadata (create migration for app_metadata)

## Iteration 15 - Task 2.3: Fix AdminProtectedRoute Logic (isInitialized flag)
- **What was implemented**: Added `isInitialized` flag to UnifiedAuthContext to prevent premature redirects
- **Files changed**:
  - `src/contexts/UnifiedAuthContext.tsx` - Added isInitialized state and exposed in context
  - `src/components/admin/AdminProtectedRoute.tsx` - Updated to wait for isInitialized before redirecting
  - `PRD.md` - Marked Task 2.3 subtasks complete, added implementation notes
- **Key changes**:
  - Added `isInitialized: boolean` to UnifiedAuthContextType interface
  - Added `useState` for `isInitialized` (starts `false`)
  - Set `isInitialized = true` after initial `getSession()` completes
  - Set `isInitialized = true` after each `onAuthStateChange` event
  - AdminProtectedRoute now checks `loading || !isInitialized` before making redirect decisions
  - This prevents the race condition where Login navigates to dashboard before context is updated
- **The redirect loop bug explained**:
  1. User calls `signInAsAdmin()` which succeeds
  2. Login.tsx navigates to `/admin/dashboard` immediately
  3. But `onAuthStateChange` hasn't fired yet
  4. AdminProtectedRoute sees `loading=false` (from initial load) but stale `user` state
  5. It redirects back to login, causing a loop
  - Fix: `isInitialized` ensures we wait for auth state to be stable after any auth event
- **Learnings for future iterations**:
  - The `loading` state in React auth contexts typically means "initial load in progress"
  - But after initial load, `loading=false` doesn't mean "auth state is current"
  - Need separate `isInitialized` flag to indicate "auth state represents reality"
  - 49 failing tests remain pre-existing - same count as before (Phase 6 work)
  - TypeScript errors in src/contexts/UnifiedAuthContext.tsx line 4 is pre-existing (@/types import)

## Iteration 46 - Task 8.4b: Apply notice_workflow_status migration to Supabase
- **What was implemented**: Applied the notice_workflow_status migration to the remote Supabase database
- **Method used**: psql with DATABASE_URL (consistent with established pattern from Iteration 40)
- **Files changed**:
  - `supabase/migrations/20260120250000_create_notice_workflow_status.sql` - Fixed is_overdue column issue
  - `PRD.md` - Marked Task 8.4b complete
- **Issue encountered and fixed**:
  - Original migration had `is_overdue BOOLEAN GENERATED ALWAYS AS (deadline_date IS NOT NULL AND deadline_date < NOW()) STORED`
  - PostgreSQL requires GENERATED column expressions to be immutable
  - `NOW()` is not immutable (changes with time), so this caused "generation expression is not immutable" error
  - **Fix**: Removed the is_overdue column; overdue status should be calculated at query time: `WHERE deadline_date IS NOT NULL AND deadline_date < NOW()`
- **Verification**:
  - Table created with 9 columns (id, notice_id, workflow_id, current_stage_id, firm_id, entered_stage_at, deadline_date, created_at, updated_at)
  - Primary key (id), unique constraint on notice_id (one status per notice)
  - 7 indexes including composite index on (firm_id, deadline_date) for overdue queries
  - Foreign keys to notices(CASCADE), workflow_configs(RESTRICT), workflow_stages(RESTRICT), organizations(CASCADE)
  - 3 RLS policies: select for members, update for editors/admins, insert for members
  - Update trigger for automatic updated_at timestamps
  - Migration recorded in supabase_migrations.schema_migrations table
- **Test results**: All 486 tests pass, no regressions
- **Learnings for future iterations**:
  - PostgreSQL GENERATED columns can only use IMMUTABLE expressions (no NOW(), CURRENT_TIMESTAMP, etc.)
  - For computed columns involving current time, calculate at query time or use views
  - Alternative: Use a trigger to update a regular column periodically, but this adds complexity
  - The `deadline_date < NOW()` condition should be added in queries/views, not stored
